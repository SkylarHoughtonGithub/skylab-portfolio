## The problem

Personal infrastructure doesn't need an internal developer platform. Running an _actual_ platform on it does — with real tool boundaries, a GitOps audit log, a service catalog, and a story for how a workload actually gets to a cluster. The first iteration of Skylab mixed delivery, infrastructure, and application concerns across eight environment-split ApplicationSets and three argo-\* repos. It worked, but it couldn't absorb a new tool without touching every layer. The rework is a rebuild from clean layer boundaries.

## What I built

Five public repos, one tenant source on an in-cluster Gitea, one deployment story per layer.

| Layer | Repo | Owns |
| --- | --- | --- |
| Delivery | [`skylab-gitops`](https://github.com/SkylarHoughtonGithub/skylab-gitops) | Everything Argo CD syncs: wrapper charts, cluster config, workloads |
| Foundations | [`skylab-terraform`](https://github.com/SkylarHoughtonGithub/skylab-terraform) | AWS + GCP: OIDC, Roles Anywhere, buckets, trust anchor |
| Infrastructure API | [`skylab-crossplane`](https://github.com/SkylarHoughtonGithub/skylab-crossplane) | Cloud-agnostic XRDs with AWS and GCP compositions, published as an OCI package |
| Front door | [`skylab-backstage`](https://github.com/SkylarHoughtonGithub/skylab-backstage) | Catalog, golden-path templates, MCP actions for AI clients |
| Remediation | [`tack-ai`](https://github.com/SkylarHoughtonGithub/tack-ai) | Policy-governed coding agent, tamper-evident audit |

Every layer has a "never touches" rule. Argo CD syncs Git state; it does not reconcile anything KubeVela renders downstream. Crossplane owns cloud resources; it does not install Helm releases. KubeVela describes application shape; it does not decide cluster placement. The discipline is the point — overlapping layers fight each other.

## A decision I'd defend: sync waves with the Application health check restored

Platform components have strict ordering (cert-manager before issuers, External Secrets Operator before ClusterSecretStores, Crossplane providers before the Configuration package, KubeVela before components, workloads last). Argo CD has sync waves for exactly this — but Argo CD 1.8 quietly dropped the built-in health check for `argoproj.io/Application` resources, which means a wave of Applications applies but never actually waits on downstream health. The fix is a Lua health hook in `argocd-cm`:

```yaml
# argocd-cm — re-enables Application health assessment so sync waves actually wait
resource.customizations.health.argoproj.io_Application: |
  hs = {}
  hs.status = "Progressing"
  hs.message = ""
  if obj.status ~= nil and obj.status.health ~= nil then
    hs.status  = obj.status.health.status
    hs.message = obj.status.health.message or ""
  end
  return hs
```

With that one hook, wave -2 (Argo CD self-managed) brings up the delivery plane, wave -1 brings up cert-manager + ESO, wave 0 brings up the trust layer, wave 1 brings up Crossplane + providers, wave 2 pins the `skylab-crossplane` Configuration, wave 3 is KubeVela, waves 4–6 are developer tools (Gitea, observability, Backstage), and wave 10 is workloads. A fresh cluster bootstraps deterministically — not "mostly in order."

## A decision I'd defend: cluster-as-data instead of path-based environments

Most Argo CD repos I've read have `envs/dev/` and `envs/prod/` folders with an ApplicationSet per folder. It scales poorly — a new cluster is a new folder and copied YAML, promotion is a two-folder edit, and the implicit "which cluster is this for" lives in paths.

Skylab is one root ApplicationSet with a cluster generator. Each cluster is an Argo cluster `Secret` with labels (`cloud`, `region`, `env`, `role`). Per-cluster config is one YAML in `clusters/`. Values layer: `values.yaml` → `values-<env>.yaml` → `clusters/<name>.yaml` with `ignoreMissingValueFiles: true`.

```yaml
# bootstrap/root-applicationset.yaml — one generator, N clusters
spec:
  generators:
    - clusters: {}        # every cluster Secret becomes a generator parameter
  template:
    spec:
      source:
        repoURL: https://github.com/SkylarHoughtonGithub/skylab-gitops
        path: charts/skylab-apps
        helm:
          valueFiles:
            - values.yaml
            - values-{{ metadata.labels.env }}.yaml
            - ../../clusters/{{ name }}.yaml
          ignoreMissingValueFiles: true
```

Adding a new cluster is two files (one labeled `Secret` + one `clusters/<name>.yaml`). No ApplicationSet copies. Promotion from dev to prod is editing one line.

## The rest of the decision log

More decisions are documented as ADRs in [`skylab-gitops/docs/adr/`](https://github.com/SkylarHoughtonGithub/skylab-gitops/tree/main/docs/adr) — wrapper chart per component (not one umbrella, not kustomize), OCI chart promotion (not branch-per-env), hub-and-spoke fleet with cloud-agnostic XRDs, one GitOps repo + tenants on Gitea, label placement now and Open Cluster Management later.

## Result

One command brings a cluster from empty to every wave healthy (`task dev:up`). New workloads are a Backstage golden-path template run that opens a PR against `platform/tenants`; Argo CD picks it up from there. A new EKS cluster is a `KubernetesCluster` XR with `cloud: aws`; the same XR with `cloud: gcp` becomes a GKE cluster. A Postgres dependency is a `postgres` KubeVela component that composes to RDS or CloudSQL by platform policy, never by developer choice.

The first workload riding the golden path is [`mechatracker`](https://github.com/SkylarHoughtonGithub/mechatracker), which deploys as a KubeVela Application and gets its database through the Postgres XRD.
